# 검증 전략

각 작업을 "끝났다"고 판정하는 방법을 정의한다. 작업 착수 전에 해당 단계의 검증
방법과 임계값을 먼저 확인하고, 임계값은 작업 시작 **전에** 고정한다.
사후에 임계값을 조정하면 검증이 아니라 사후 합리화가 된다.

## 왜 어려운가

이 저장소의 산출물 대부분은 역할 계약 문서다. 프롬프트는 단위 테스트가 되지 않는다.
기존 `npm run check`는 **구조**만 검증한다. 패키지가 올바르게 설치되고 파일이
일관적인지는 보지만, 역할이 올바르게 **행동**하는지는 전혀 보지 않는다.

이 문서는 그 공백을 메우는 4단계 사다리를 정의한다.

## 검증 사다리

| 단계 | 대상 | 방법 | 속도/비용 | 실행 시점 |
|---|---|---|---|---|
| **L1 구조** | 선언의 일관성 | `npm run check` 확장 | 즉시 / 무료 | CI 매번 |
| **L2 렌더링** | 산출 파일의 형태 | 골든 스냅샷 비교 | 즉시 / 무료 | CI 매번 |
| **L3 동작** | 역할의 계약 준수 | 시나리오 실행 후 기계 판정 | 분 단위 / 유료 | 수동 + 릴리스 전 필수 |
| **L4 통합** | 실제 일을 끝내는가 | 미니 프로젝트, 사람 판정 | 일 단위 / 비쌈 | Phase 2 |

---

## L1 — 구조 검증

기존 `validate`를 작업마다 확장한다. 기계적이고 결정론적이므로 **통과율 100%를 요구**한다.

검증 항목 (작업 진행에 따라 누적):

- manifest 역할 수 = 배포되는 agent 수 (1.1)
- 모든 SKILL.md에 Activation / Done Criteria / Stop Conditions 존재 (1.2)
- 핸드오프 템플릿의 필수 필드 존재 (1.3)
- manifest에 등장하는 모든 도구명의 타깃 매핑 존재 (1.4)
- 모든 `consumes`가 어떤 역할의 `produces`에 존재 (1.8)
- 의존성 그래프에 순환 없음, 도달 불가 역할 없음 (1.8)

각 작업의 완료 기준 대부분이 여기 해당한다. **먼저 검사를 추가하고, 그 검사가 실패하는
것을 확인한 뒤, 통과시킨다.** 통과하는 검사를 나중에 붙이면 아무것도 검증하지 못한다.

---

## L2 — 렌더링 검증

1.1에서 `manifest + SKILL.md → 타깃별 산출물` 렌더링을 도입하면 필수가 된다.
렌더링은 한 곳을 고치면 여러 파일이 바뀌므로, 의도하지 않은 변경을 스냅샷으로 잡는다.

```
tests/golden/
├── codex/planner.toml
├── codex/feature-orchestrator.SKILL.md
├── claude/role-planner.CLAUDE.md
└── cursor/role-planner.SKILL.md
```

- 렌더링 결과와 골든 파일을 바이트 단위 비교한다
- 차이가 나면 실패시키고, 의도된 변경이면 골든을 갱신하는 커밋을 따로 만든다
- **골든 갱신 커밋에는 반드시 diff 요약을 남긴다.** 무심코 갱신하면 스냅샷은
  검증 장치가 아니라 통과 도장이 된다

임계값: 100% 일치.

---

## L3 — 동작 검증

가장 중요하고 가장 설계가 필요한 단계다. 1.3(핸드오프 스키마) 완료 후에 만들 수 있다.
판정할 스키마가 없으면 판정할 수 없기 때문이다. **1.6(의존성 디스패치) 착수 전까지
반드시 만든다.** 1.6은 Phase 1에서 가장 큰 변경이며 검증 없이 진행하면 안 된다.

### 핵심 원칙: 판정 가능한 것만 판정한다

동작 검증이 어렵다고 생각되는 이유는 "기획이 좋은가"를 판정하려 하기 때문이다.
그것은 포기하고, 기계가 판정할 수 있는 것에 집중한다.
**실제 실패의 대부분은 품질 문제가 아니라 계약 위반이다.**

| 기계 판정 가능 | 사람만 판정 가능 |
|---|---|
| 핸드오프에 필수 필드가 있는가 | 기획이 타당한가 |
| `facts_confirmed`의 출처 경로가 실재하는가 | 디자인이 적절한가 |
| 어떤 역할이 선택되었는가 | 코드가 우아한가 |
| `out_of_scope` 파일을 수정했는가 (git diff) | |
| Stop 조건이 발동했는가 | |
| 스텝 수 / 재진입 횟수가 상한 내인가 | |

왼쪽은 자동화하고, 오른쪽은 릴리스 전 **샘플링**해서 기록만 남긴다. 게이트로 쓰지 않는다.

### 시나리오 파일

```
tests/eval/cases/
├── R1-new-feature-cold.md      # 문서 없는 신규 기능
├── R2-trivial-edit.md          # 사소한 단일 수정
├── R3-resume-with-articulate.md
└── R4-gap-discovered.md
```

각 케이스는 고정 입력(요청 + 초기 저장소 상태)과 기대값을 담는다.

### 라우팅 케이스 테이블

1.6의 핵심 검증이다. 고정 체인을 폐기하면서 **그 자리에 들어가는 것**이 이 표다.
체인이 아니라 기대값이라는 점이 다르다 — 디스패처가 어떤 경로로 도출하든 상관없고,
입력 상태에 대한 출력만 본다.

| 케이스 | 요청 | 초기 상태 | 기대 선택 | **금지** |
|---|---|---|---|---|
| R1 | "온보딩 기능 만들어줘" | 문서 없음 | analyst + planner 병렬 시작 | developer 즉시 선택 |
| R2 | "버튼 색만 바꿔줘" | - | developer 단독 | planner/designer 활성화 |
| R3 | "온보딩 기능 만들어줘" | articulate 존재 | planner 건너뜀 | planner 재실행 |
| R4 | 조사 중 기획 공백 발견 | - | planner 재진입 1회 | 재진입 2회 초과 |
| R5 | "이 버그 고쳐줘" | - | developer (+qa) | analyst 활성화 |

**"금지" 열이 "기대" 열만큼 중요하다.** 동적 라우팅의 주된 실패 모드는 필요한 역할을
빠뜨리는 것이 아니라 **불필요한 역할을 부르는 것**이며, 그것이 비용과 지연의 주범이다.
R2와 R5가 과잉 위임을 잡는 케이스다.

### 비결정성 처리

LLM 실행은 결정론적이지 않다. 케이스마다 n회(기본 5회) 반복하고 통과율로 판정한다.

| 판정 항목 | 임계값 | 근거 |
|---|---|---|
| 핸드오프 구조 준수 | 5/5 (100%) | 구조는 결정론적이어야 한다. 실패는 계약 결함 |
| `out_of_scope` 경계 준수 | 5/5 (100%) | 위반은 타협 불가 |
| 출처 경로 실재 | 5/5 (100%) | 없는 파일을 근거로 대면 계약 위반 |
| 라우팅 정확도 | 4/5 (80%) | 판단이 개입하므로 변동을 허용 |
| 금지 역할 미활성화 | 5/5 (100%) | 과잉 위임은 무조건 실패 |

실패한 회차는 원인을 세 가지로 분류해 기록한다: **계약 결함 / 컨텍스트 부족 /
모델 변동**. 계약 결함만 고치고, 모델 변동은 임계값으로 흡수한다.

### 비용 정책

L3는 실제 LLM 호출이므로 CI에서 매번 돌리지 않는다.

- `npm run eval` — 수동 실행
- 릴리스 전 필수 실행, 결과를 `docs/development/eval-history/`에 기록
- 1.6처럼 라우팅을 바꾸는 작업은 전후 비교 필수

## 실패 시 행동

임계값 미달 시 무엇을 할지 미리 정한다.

| 상황 | 행동 |
|---|---|
| L1 실패 | 즉시 수정. 커밋하지 않는다 |
| L2 실패 (의도치 않은 diff) | 렌더링 로직 수정. 골든을 먼저 고치지 않는다 |
| L2 실패 (의도된 변경) | 골든 갱신을 별도 커밋으로, diff 요약 포함 |
| L3 계약 결함 | 역할 계약 수정 후 재실행 |
| L3 컨텍스트 부족 | 핸드오프 스키마 또는 입력 보강 |
| L3 모델 변동 | 통과율이 임계값 내면 수용, 기록만 |
| L3 임계값 미달 지속 | **작업을 미완료로 되돌린다.** 체크박스를 채우지 않는다 |
