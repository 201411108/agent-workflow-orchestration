# 설계 결정 기록

이 문서는 워크플로 시스템의 확정된 설계 결정과 그 근거를 기록한다.
로드맵의 개별 작업은 여기 기록된 결정을 전제로 수행한다.
결정을 바꾸려면 이 문서를 먼저 갱신하고, 그 다음에 로드맵과 구현을 조정한다.

상태 값: `확정` | `잠정` | `폐기`

---

## D1. 역할은 직군이 아니라 실행 단위로 나눈다

- 상태: 확정
- 결정일: 2026-09-20

회사 직군(기획자, 디자이너, 데이터 엔지니어)을 그대로 역할로 옮기지 않는다.
직군은 사람의 고용과 커리어 단위로 나뉜 것이며 작업의 자연스러운 분할이 아니다.
역할이 늘수록 핸드오프 비용은 제곱으로 늘고 각 단계의 신호는 희석된다.

역할을 분리하는 기준은 다음 셋이며, 셋 중 둘 이상을 만족할 때만 새 역할로 만든다.

1. 읽어야 할 컨텍스트 소스가 완전히 다른가
2. 변경 권한(`mutationPolicy`)이 다른가
3. 산출물이 독립적으로 검증 가능한가

이 기준의 적용 결과:

- 시장 조사는 `role-researcher`(내부 코드/문서 근거)와 `role-analyst`(외부 시장/지표)로
  분리한다. 읽는 소스와 도구가 완전히 다르다.
- 데이터 파이프라인 구축은 별도 역할로 만들지 않는다. 코드를 쓰는 일이므로
  `role-developer`의 권한과 동일하다. 필요한 것은 지표를 읽어 다음 기획의 입력을
  만드는 역할이며 `role-analyst`가 담당한다.
- `role-qa`를 신설한다. 기존 `role-reviewer`는 `mutationPolicy: none`이라 테스트를
  작성할 수 없고, 그 결과 자율 루프의 게이트를 만들 주체가 없다.

## D2. 고정 체인을 폐기하고 의존성 해소로 라우팅한다

- 상태: 확정
- 결정일: 2026-09-20

기존 오케스트레이터는 `요청 유형 → 고정 역할 순서` 표를 갖는다. 이 방식은 역할을
추가할 때마다 표를 손으로 고쳐야 하고, 표에 없는 요청은 억지로 분류되며, 실행 중에
드러난 사실을 반영하지 못한다.

대신 각 역할이 자기 능력과 입출력을 선언하고, 디스패처가 "아직 없는 산출물"을 기준으로
매 스텝 라우팅을 다시 계산한다. 빌드 시스템의 의존성 해소와 같은 구조다.

역할 선언(`agent-workflow.manifest.json`):

```json
{
  "name": "role-analyst",
  "capabilities": ["market-research", "metric-analysis", "competitor-scan"],
  "produces": ["market_evidence", "metric_report"],
  "consumes": ["user_request"],
  "mutationPolicy": "none"
}
```

디스패치 절차:

1. 요청을 목표 산출물 집합으로 변환한다.
2. 아직 생산되지 않은 산출물 중, `consumes`가 이미 충족된 것을 고른다.
3. 그것을 `produces`하는 역할을 실행한다. 조건을 만족하는 역할이 여럿이면
   D3의 병렬 규칙에 따라 동시에 실행한다.
4. 산출물을 상태에 반영하고 2로 돌아간다. 매 스텝 재계산하며,
   앞 단계 산출물이 목표 집합 자체를 바꿀 수 있다.
5. 목표 산출물이 모두 채워지거나 D6의 경계 조건에 걸리면 종료한다.

이 구조의 이점:

- 역할 추가 시 라우팅 표 수정이 불필요하다. 선언만 추가하면 된다.
- 병렬 가능 지점이 자동으로 도출된다.
- 순환 의존과 생산자 없는 소비를 `validate`로 기계 검증할 수 있다.

## D3. 병렬 실행은 mutationPolicy로 결정한다

- 상태: 확정
- 결정일: 2026-09-20

하나의 지시에 대해 둘 이상의 역할이 동시에 일할 수 있어야 한다. 다만 무제한 병렬은
파일 충돌을 만든다. 기존 `mutationPolicy` 값이 그대로 병렬성 판정 기준이 된다.

| mutationPolicy | 병렬 실행 | 근거 |
|---|---|---|
| `none` | 제한 없음 | 파일을 쓰지 않으므로 충돌 불가 |
| `docs-only` | 대상 문서 경로가 서로소일 때만 | 같은 문서 동시 편집 방지 |
| `implementation` | 항상 단독 | 코드 변경은 직렬화한다 |

실무상 `role-researcher`, `role-analyst`, `role-architect`는 함께 출발할 수 있고,
`role-developer`는 언제나 혼자 돈다.

## D4. 에이전트 간 직접 대화를 금지하고 질문을 반환하게 한다

- 상태: 확정
- 결정일: 2026-09-20

"에이전트들이 서로 소통한다"를 자유 대화로 구현하지 않는다. 자유 대화는 종료를
보장하지 못하고, 실행 경로를 재현할 수 없어 디버깅이 불가능하며, 비용이 예측되지
않는다. 에이전트끼리의 합의에는 틀렸다는 신호가 없어서 초기 오해가 대화가 길어질수록
사실로 굳는다.

대신 다음 프로토콜을 쓴다. 역할 B가 역할 A의 결정이 필요하면 B는 A를 호출하지 않고
`blocking_questions`에 질문을 담아 디스패처로 반환한다. 디스패처가 A를 다시 호출해
답을 얻고 B를 재개한다.

```
B → (blocking_question) → 디스패처 → A → (답) → 디스패처 → B 재개
```

결과적으로 협업은 일어나지만 모든 경로가 디스패처를 통과하므로 기록, 상한, 재현이
가능하다. 이것이 "알아서 하되 예측 가능한" 지점이다.

## D5. 핸드오프는 frontmatter와 본문의 하이브리드로 고정한다

- 상태: 확정
- 결정일: 2026-09-20

자연어 마크다운 핸드오프는 다음 역할이 매번 재해석해야 하고, "사실과 가정을 구분하라"
같은 지시가 문장으로만 존재해 강제되지 않는다. 반대로 완전 JSON은 LLM 산출 품질을
떨어뜨린다. 기계가 읽을 부분은 frontmatter로, 판단이 필요한 부분은 본문으로 나눈다.

```markdown
---
from: role-planner
to: role-developer
work_id: user-onboarding
produced: [articulate_doc]
facts_confirmed:
  - { claim: "...", source: "path/to/file.ts:42" }
assumptions:
  - { claim: "...", risk: high }
blocking_questions: []
out_of_scope: ["결제 흐름", "기존 세션 로직"]
---

## 결정 사항
## 다음 역할이 확인할 것
```

강제되는 세 가지:

- `facts_confirmed`는 출처 경로가 필수다. 출처 없는 항목은 `assumptions`로 간다.
- `blocking_questions`가 비어 있지 않으면 디스패처가 루프를 멈춘다.
- `out_of_scope`는 필수 필드다. 자율 에이전트의 최대 실패 모드는 멈춤이 아니라
  범위 확장이며, 매 핸드오프에서 범위 밖을 명시해야 누적 확장을 막는다.

## D6. 경계 조건을 디스패처에 내장한다

- 상태: 확정
- 결정일: 2026-09-20

동적 라우팅은 종료 보장이 없다. 아래 조건을 디스패처가 직접 검사하며, 하나라도
걸리면 즉시 중단하고 사람에게 반환한다. 이 조건들은 나중에 붙이는 안전장치가 아니라
디스패처 최초 구현의 일부다.

| 조건 | 기본값 | 목적 |
|---|---|---|
| `maxSteps` | 12 | 전체 역할 호출 수 상한 |
| `maxReentry` | 2 | 같은 역할 재호출 상한, 핑퐁 방지 |
| `noProgressLimit` | 2 | 연속 스텝에서 새 산출물/사실이 0개면 중단 |
| `blocking_questions` | 비어있지 않음 | 즉시 사람 호출 |
| `out_of_scope` 위반 | 감지 시 | 즉시 중단 |

`noProgressLimit`이 핵심 순환 방지 장치다. 산출물 집합과 `facts_confirmed` 개수만
비교하면 되므로 기계적으로 판정할 수 있다.

## D7. 자율성의 상한은 검증 가능성이 결정한다

- 상태: 확정
- 결정일: 2026-09-20

기계가 판정할 수 있는 만큼만 사람 없이 돌릴 수 있다. 역할을 늘리거나 프롬프트를
정교하게 만드는 것으로는 이 선을 넘지 못한다. LLM 리뷰어의 승인은 의견이지 사실이
아니다.

따라서 `role-qa`를 `role-developer` **앞**에 배치한다. 수용 기준이 실행 가능한
테스트가 된 뒤에 구현이 시작되면, developer의 완료 판정이 의견이 아니라 사실이 된다.
이것이 Phase 3 자율 루프의 전제 조건이다.

`articulate.md`의 수용 기준을 산문에서 체크 가능한 형태로 바꾸는 작업이 여기에 물린다.

## D8. 새 에이전트 런타임을 만들지 않는다

- 상태: 확정
- 결정일: 2026-09-20

드라이버는 기존 헤드리스 하네스(`codex exec`, `claude -p`)를 `child_process`로
호출하는 얇은 Node 스크립트로 구현한다. LangGraph나 Temporal 같은 워크플로 엔진은
현재 규모에 과하다. 동시 실행 작업이 수십 개가 되는 시점에 재검토한다.

현재 `bin/cli.js`에는 `child_process`가 전혀 없다. 드라이버는 이 경계를 넘는
첫 번째 구성 요소가 된다.

## D9. 자율 모드에서는 기존 안전 규칙 두 개를 뒤집는다

- 상태: 확정
- 결정일: 2026-09-20

`AGENTS.md`의 다음 두 규칙은 사람이 운전할 때의 안전 규칙이며, 자율 루프에서는
방해물이 된다. Phase 3.2 시점에 자율 모드에 한해 반전한다.

| 현재 규칙 | 자율 모드 |
|---|---|
| 수동 상태 파일을 SSoT로 보지 않는다 | `work.json`이 기계 판독 SSoT가 된다 |
| 현재 체크아웃된 브랜치를 그대로 쓴다 | 작업마다 격리된 worktree를 쓴다 |

격리 없이는 실패한 시도를 버릴 수 없고, 버릴 수 없으면 재시도가 안전하지 않다.
사람이 직접 운전하는 모드에서는 기존 규칙을 유지한다.

## D10. 개발 레이어와 제품 레이어를 분리한다

- 상태: 확정
- 결정일: 2026-09-20

이 저장소에는 두 흐름이 공존한다. 워크플로 자체를 개발하는 흐름(레이어 1)과,
npm 설치 후 사용자 프로젝트에서 동작하는 흐름(레이어 2)이다. 둘을 섞지 않는다.

| | 레이어 1 — 개발 | 레이어 2 — 제품 |
|---|---|---|
| 진입점 | `CLAUDE.md`, `AGENTS.md` | 설치 시 생성되는 `.claude/skills/` 등 |
| 상태 | `docs/development/ROADMAP.md`, `DEVLOG.md` | `.agent-workflow/` |
| 소스 | `docs/development/` | `skills/`, `adapters/`, `templates/`, `payloads/`, `bin/` |

**레이어 1은 레이어 2를 사용하지 않는다.** 이 저장소의 개발에 제품 역할
(`role-planner`, `role-developer` 등)을 쓰지 않는다. 근거는 셋이다.

1. 제품 역할은 소비자 프로젝트의 기능을 구현하도록 설계되었다. 오케스트레이션
   패키지 자체를 진화시키는 작업(역할 계약 수정, manifest 스키마 변경, 어댑터 렌더링)은
   어떤 제품 역할의 책임도 아니다.
2. 자기가 서 있는 바닥을 리팩터링하게 된다. 1.5에서 라우팅을 통째로 교체하는데
   그 라우팅으로 작업하고 있으면 실패 원인이 변경 때문인지 작업 방식 때문인지
   분리할 수 없다.
3. 자기 자신에 설치하는 것은 제품 검증이 아니다. 실제 검증은 Phase 2에서
   별도 미니 프로젝트로 수행한다.

### 위반 해소 (2026-09-20)

루트의 `.codex/agents/*.toml` 3개와 `.agents/skills/feature-orchestrator/SKILL.md`는
레이어 2 메커니즘을 저장소 자신에 적용한 것이었고, `payloads/codex/`의 사본과 이미
드리프트했다(루트 한국어, payload 영어). 손으로 두 벌을 관리하는 구조여서 언어 차이가
시간이 지나면 내용 차이가 된다.

ROADMAP 1.0에서 A안(제거)을 채택해 네 파일을 삭제했다. 삭제 전 참조를 확인한 결과
`bin/cli.js`의 모든 참조는 `payloads/codex/` 또는 설치 대상 경로를 가리켰으며 루트
사본에 의존하는 코드는 없었다.

`.codex/config.toml`은 A의 범위 밖이라 보존했다. custom agent 없이 multi-agent만
켜둔 상태이며 동작 영향은 없다. 처리 방침은 ROADMAP 1.1에서 함께 정한다.

## D11. 세션 연속성은 마크다운 3종으로 유지한다

- 상태: 확정
- 결정일: 2026-09-20

새 세션이 맥락을 잃지 않으려면 다섯 가지가 필요하다. 각각의 책임 파일을 고정한다.

| 필요한 것 | 파일 |
|---|---|
| 지금 어느 단계인가 | `ROADMAP.md` 현재 상태 |
| 다시 논쟁하면 안 되는 전제 | `DESIGN_DECISIONS.md` |
| git에 남지 않는 맥락 | `DEVLOG.md` |
| 코드 상태 | git log / status |
| 정상 여부 판정 | `npm run check` |

git 이력이 주지 못하는 것은 셋이다. 왜 멈췄는지, 무엇을 시도하다 버렸는지,
사용자 확인을 기다리는 가정이 무엇인지. `DEVLOG.md`가 이것만 담당하며
`작업 / 결정 / 미해결 / 다음` 네 필드로 고정한다. 필드를 늘리면 유지되지 않는다.

레이어 1의 상태를 기계 판독용 JSON으로 만들지 않는다. 이 상태를 읽는 주체가
사람과 LLM뿐이므로 마크다운이 마찰이 낮다. 기계 판독 상태는 Phase 3.2에서
드라이버가 `work.json`을 소비할 때 도입하며, 그것은 레이어 2의 일이다.

## D12. 검증은 4단계 사다리로 하고 임계값을 미리 고정한다

- 상태: 확정
- 결정일: 2026-09-20

기존 `npm run check`는 구조만 검증한다. 패키지가 올바르게 설치되는지는 보지만 역할이
올바르게 행동하는지는 전혀 보지 않는다. 이 공백을 4단계로 메운다. 각 단계의 대상,
임계값, 실행 시점, 실패 시 행동은 [VERIFICATION.md](./VERIFICATION.md)에 있다.

| 단계 | 대상 | 실행 시점 |
|---|---|---|
| L1 구조 | 선언의 일관성 | CI 매번 |
| L2 렌더링 | 산출 파일의 형태 | CI 매번 |
| L3 동작 | 역할의 계약 준수 | 수동 + 릴리스 전 |
| L4 통합 | 실제 일을 끝내는가 | Phase 2 |

확정하는 원칙 셋:

1. **판정 가능한 것만 판정한다.** "기획이 좋은가"는 자동 판정하지 않는다. 대신
   계약 준수(필수 필드, 출처 실재, 역할 선택, 경계 준수, 상한 준수)를 기계로 본다.
   실제 실패의 대부분은 품질 문제가 아니라 계약 위반이다.
2. **임계값을 작업 착수 전에 고정한다.** 사후 조정은 검증이 아니라 사후 합리화다.
   구조·경계·출처는 100%, 라우팅 정확도는 80%로 시작한다.
3. **검사를 먼저 추가하고 실패를 확인한 뒤 통과시킨다.** 통과하는 검사를 나중에
   붙이면 아무것도 검증하지 못한다.

L3 하네스는 1.3(핸드오프 스키마) 이후에만 만들 수 있고, 1.6(의존성 디스패치) 이전에
반드시 있어야 한다. 1.6은 Phase 1에서 가장 큰 변경이며 검증 없이 진행하지 않는다.
따라서 1.5를 검증 하네스 작업으로 신설한다.
