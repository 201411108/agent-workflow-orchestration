# Phase 2 실험 설계 — 계기 문서

**상태: 동결 (2026-09-28). 스텝 1 착수 후에는 고치지 않는다.**

이 문서는 Phase 2의 측정 규칙을 정한다. 실행 중에 이 문서를 고치면 지표가 움직이는
표적을 기술하게 되므로, 변경이 필요하면 **세그먼트 경계**에서만 한다
(§9 참조). 변경 이력은 문서 맨 아래 §12에 남긴다.

---

## 1. 무엇을 만드는 단계인가

**산출물은 서비스가 아니라 분류된 개입 기록이다.** 서비스는 개입을 발생시키는 부하다.

Phase 2가 답해야 하는 질문은 하나다.

> 사람이 개입해야 했던 지점 중, 무엇이 고칠 수 있는 것이고 무엇이 영구적으로
> 사람의 몫인가.

`판단 필요`로 분류된 것은 Phase 3에서 **영구 사람 체크포인트**가 되고, 나머지는
고쳐서 **자동화 범위**에 들어간다. 이 분류가 Phase 3의 범위를 그대로 결정한다.

**드라이버나 자동 루프를 만들지 않는다.** 먼저 넣으면 실패 원인이 역할 정의인지
드라이버인지 분리할 수 없다. 한 스텝 = 한 디스패치를 사람이 돌린다.

### 대상

`/Users/hankim/Desktop/workspace/clean-the-code` — 코드 스멜 연습 서비스.
제품 명세는 그 저장소의 `BRIEF.md`에 있다. 이 문서는 명세가 아니라 **계기**다.

---

## 2. 계기는 이 저장소에 둔다 — 대상 저장소가 아니다

```
docs/development/phase2/
├── README.md          # 이 문서. 실험 설계. 동결
├── RUNLOG.md          # 스텝 단위 기록 (append-only)
├── INTERVENTIONS.md   # 개입 1건 = 1행
├── DECISIONS.md       # 결정 레지스터 (핸드오프 손실 판정의 기준선)
└── envelopes/S<n>-<role>.yaml
```

**왜 대상 저장소에 두지 않는가**: 역할은 자기가 일하는 저장소를 읽는다.
"planner가 제약을 빠뜨렸다"는 메모가 `clean-the-code`에 있으면 다음 역할이 그것을
읽고, **관찰이 관찰 대상을 오염시킨다.** D10의 레이어 분리를 관찰에 적용한 것이다.

30~60행 규모에 파서를 쓰지 않는다. "자동화를 만들지 않는다"는 이 단계의 금지 사항이다.

---

## 3. 스텝 기록 (`RUNLOG.md`)

한 스텝 = 한 디스패치. 매 스텝 후 아래 블록을 **추가만** 한다. 지우거나 고치지 않는다.

```markdown
### S07 — role-developer — 2026-09-29T14:20 — seg1
- 입력: "articulate + test_plan 기준으로 채점 어댑터를 구현한다"
- 배정: orchestrator | 사람 지명
- 봉투: status=complete produced=[specs_doc,change_summary,verification]
        needs=[] facts=6 assumptions=2 out_of_scope=[problems/, ui/]
- diff: src/grader/client.ts problems/003/rubric.json
- 게이트: npm test → fail (2 failing)   [1회 통과: ✗]
- 범위이탈: problems/003/rubric.json (out_of_scope에 선언됨) → 1건
- 개입: I12, I13
```

세 줄은 붙여넣고 둘만 쓴다. `봉투`·`diff`·`게이트`는 기계 출력을 옮기고,
`범위이탈`과 `개입`만 판단이 들어간다.

### 범위 이탈은 기계적으로 센다

```
git diff --name-only  ∩  (봉투의 out_of_scope ∪ 그 스텝에 선언된 범위 밖)
```

그래서 **스텝 1 전에 최초 커밋이 있어야 한다.** 빈 저장소에서는 diff가 없다.

### 게이트는 `role-qa`가 만든 테스트만 센다

`role-reviewer`의 `verdict`는 기록하되 **게이트가 아니다.** LLM 리뷰어의 승인은
의견이지 사실이다가 아니다 (D7). `[1회 통과]`는 그 스텝에서 사람 개입 없이 게이트를
통과했는지이며, Phase 3 자율 루프의 직접 선행 지표다.

---

## 4. 개입 하나의 정의

> 역할 스레드에 들어간 사람의 메시지 중, (a) 그 스텝의 최초 과제 진술과
> (b) 앞 역할 봉투의 그대로 전달이 **아닌** 것.

| 행위 | 개입 수 |
|---|---|
| 차단 질문에 답 | 1 |
| 산출물 교정 요구 | 1 |
| 과제를 재작성해 재실행 | 1 |
| 승인 ("좋아, 계속") | **0** |
| 오케스트레이터가 고르지 않은 역할을 사람이 지명 | 1 + `디스패치 개입` 표시 |
| 사람이 제품 코드를 직접 씀 | 1 + **그 스텝의 게이트 데이터 무효** |

마지막 줄이 중요하다. 사람이 구현해 놓고 통과한 게이트는 워크플로의 성적이 아니다.

## 5. 분류 — 순서가 있는 판정, 먼저 맞는 것이 이긴다

`판단 필요`는 유인력이 있다. 분류 안 된 것이 전부 거기 빨려들면 Phase 3 범위가
0이 된다. 그래서 **Q1 → Q2 → Q3 순서로 묻고 먼저 맞는 곳에서 멈춘다.**

### Q1 → `컨텍스트 부족`

> 역할이 닿을 수 있는 곳에 **이미 있던** 사실이 입력에 들어 있었다면 이 개입이
> 불필요했는가?

**통과 조건: 그 경로와 줄, 또는 답을 담고 있던 핸드오프 필드를 적어야 한다.**
적을 수 없으면 Q1이 아니다.

부가 태그:
- `미전달` — 상류 역할이 알고 있었으나 봉투에 넘기지 않았다
- `미탐색` — 역할이 읽을 수 있었으나 찾지 않았다

### Q2 → `역할 정의 결함`

> 계약·manifest·템플릿·어댑터에 **문장 하나를 넣거나 고쳐** 재발을 막을 수 있는가?
> 프로젝트 고유 사실을 넣지 않고?

**통과 조건: 기록 시점에 대체 문장을 실제로 써야 한다.**
이 규칙이 기록을 곧바로 Phase 1 되감기 입력으로 만든다. 나중에 쓰겠다고 비워두면
종료 시 그 개입은 쓸 수 없다.

"프로젝트 고유 사실을 넣지 않고"가 핵심 제약이다. `clean-the-code`의 사정을 역할
계약에 넣으면 그것은 수정이 아니라 오염이다.

### Q3 → `판단 필요`

**둘 다 참이어야 하고 둘 다 기록해야 한다.**

1. 사람 머릿속에만 있는 선호·가치·사업 맥락에 달려 있다
2. **어떤 문서나 외부 자료도 결정할 수 없다**

문서가 결정할 수 있으면 `컨텍스트 부족`이고, 고칠 것은 "그 문서를 쓰는 것"이다.

### 직교 플래그: `재현 = 반복 | 1회`

Phase 1에서 가장 유용했던 판별자다. R6이 계약 결함으로 분류된 근거가 "매번 같은
형태"였고, R7의 봉투 플레이스홀더 복사가 계약 결함이 아니라 잔차로 분류된 근거가
"3/4 통과"였다.

**이 플래그가 없으면 모델 변동이 역할 정의 결함으로 세탁되고 Phase 3이 유령을 쫓는다.**
`1회`로 보이는 것을 `반복`으로 올리려면 같은 형태를 두 번 이상 봐야 한다.

### 기록 형식 (`INTERVENTIONS.md`)

표 + **분류 1·2번에만** 상세 블록. 쓰는 노력을 Phase 3 입력이 나오는 곳에만 쓰는
의도적 마찰 설계다.

```markdown
| ID | 스텝 | 분류 | 재현 | 한 줄 |
|----|------|------|------|-------|
| I12 | S07 | 컨텍스트 부족(미전달) | 반복 | 채점 스키마 버전 필드를 developer가 몰랐다 |
| I13 | S07 | 역할 정의 결함 | 1회 | out_of_scope를 선언하고도 그 경로를 고쳤다 |
| I14 | S08 | 판단 필요 | — | 점수 척도를 3단계로 할지 5단계로 할지 |

#### I12 — 컨텍스트 부족 (미전달)
- 답이 있던 곳: `docs/DECISIONS.md` D004 / S02 봉투 `facts_confirmed[2]`
- 누가 안 넘겼나: role-planner → role-developer 핸드오프

#### I13 — 역할 정의 결함
- 대체 문장: (계약에 넣을 문장을 여기 실제로 쓴다)
- 넣을 곳: `skills/role-developer/SKILL.md` `## Restrictions`
```

### 종료 시 감사

`판단 필요`가 **40%를 넘으면 재검토한다.** 대부분은 Q1/Q2를 게으르게 통과시킨 것이다.

## 6. 핸드오프 손실 — 결정 레지스터로 판정 가능하게

`DECISIONS.md`에 스텝이 확정한 결정을 한 줄씩 누적한다. 이것이 손실 판정의 기준선이다.

```
D004  채점 응답은 JSON 스키마로 강제한다. 프로즈 폴백 없음.  (S02 / role-planner / articulate.md:L41)
D005  모델 호출은 테스트가 대체 가능한 경계 뒤에 둔다.        (S04 / role-architect)
```

| 유형 | 판정 규칙 |
|---|---|
| `무시` | `D<n>`과 모순되는 산출물을 냈고 `D<n>`을 **언급조차 안 했다** |
| `재결정` | `D<n>`을 언급하고 다르게 결정했다 |
| `재질문` | 이미 `D<n>`으로 답한 것을 사람에게 다시 물었다 |

**근거를 밝힌 재결정은 자동으로 결함이 아니다.** `정당`으로 표시하고 종료 시 판단한다.
새 사실이 드러나 결정을 바꾸는 것은 D2가 의도한 동작이다.

## 7. 종료 조건

**전부** 만족해야 종료한다.

1. **기능 1개가 끝에서 끝까지 돈다** — 깨끗한 체크아웃에서 명령 하나로 스키마를
   만족하는 채점 JSON이 나오고 qa 스위트가 통과한다. 실제 OpenAI 호출로 최소 1회
2. **디스패치 스텝 ≥12, 봉투 전부 확보** (12 = D6의 `maxSteps`)
3. **분류된 개입 ≥15 그리고 포화** — 마지막 5건에서 새 `역할 정의 결함` 유형이 없다.
   측정 단계의 정직한 종료는 **배우기를 멈출 때**다
4. **역할 정의 수정 ≥1건 반영** + `npm run eval` 회귀 없음
5. **종료 보고서** — 집계, 분류 히스토그램, Phase 3 범위를
   `영구 사람 체크포인트` / `자동화 대상`으로 분리

### 중단 조건

**6스텝 후에도 분류 가능한 개입이 3건 미만이면 중단한다.** 보통 사람이 계속 운전한
경우다. **프로토콜을 고치고 세그먼트 2로 다시 시작한다. 제품을 고치지 않는다.**

### 예산 상한

**5 작업 세션.** 기한 없는 측정 단계는 제품 단계가 된다. 상한에 닿으면 그 시점의
기록으로 종료 보고서를 쓴다. 종료 조건 미달이면 미달로 기록한다.

### 포화 전에 기능이 끝나면

기능을 늘리지 않는다. 같은 저장소에 **작은 두 번째 기능**을 시작한다.
"기능 하나" 제약을 지키면서 표본을 늘리고 **비어 있지 않은 저장소** 사례가 생긴다.

## 8. 되감기는 종료 시에 한다

**실행 중에는 기록만 하고 고치지 않는다.** 가면서 고치면 지표가 움직이는 표적을
기술한다.

예외는 **차단 결함**뿐이다.

- 어떤 역할도 봉투를 못 낸다
- 어떤 역할이 영원히 배정 불가다
- 제품이 역할에게 거짓 사실을 주입한다 (1.6 `Source:` 유형)

즉시 고치고 `RUN-BREAK`로 표시하며 **새 세그먼트를 연다.**

### 종료 시 절차

1. 같은 대체 문장끼리 묶는다
2. ROADMAP 2.x 항목으로 만든다
3. **결정이 바뀌면 D번호를 먼저 고친다** (CLAUDE.md 규칙)
4. 적용한다
5. **`npm run eval` 전후 비교 필수**
6. 시나리오로 표현되는 수정은 `tests/eval/cases/`에 케이스로 추가한다

R4가 선례다 — 명백히 나아 보였던 변경이 4/5 → 0/4였고 측정만이 그것을 잡았다.

## 9. 세그먼트

지표는 **세그먼트를 넘어 합치지 않는다.** 세그먼트가 갈리는 경우는 셋뿐이다.

1. `RUN-BREAK` — 차단 결함을 고쳤다
2. 이 문서(§1~§11)를 고쳤다
3. 디스패치 방식을 바꿨다 (자동 → 수동 등)

`RUNLOG.md`의 각 스텝 블록에 `seg<n>`을 적는다.

## 10. 하네스는 Claude로 한다

**먼저 오해를 없앤다. Codex도 이 툴을 정상적으로 쓸 수 있다.** 실측 기록이다
(`eval-history/2026-09-24T04-43-28-492Z-codex.json`).

```
역할 9개 로드 · 봉투 산출 · 위임 실제 발생
  R1(신규 기능) 위임 9회    R2(한 줄 수정) 위임 0회   ← 과잉 위임 없음
  R3 2회  R4 3회  R6 2회  R7 4회   R5(버그 수정) 0회
```

| | Codex | Claude |
|---|---|---|
| 역할 로드·위임 | ✅ | ✅ |
| 위임 **횟수** 관찰 | ✅ `collab_tool_call` | ✅ |
| 위임된 **역할 이름** 자동 관찰 | ❌ 스트림 메타데이터에 없다 | ✅ `subagent_type` |
| 역할 이름 **사람 관찰** | ✅ 오케스트레이터의 `active_roles` 텍스트 | ✅ |
| 역할별 도구 허용 목록 | ❌ `sandbox_mode`만 (D17) | ✅ `tools` |

Claude를 고르는 이유는 **"Codex가 라우팅을 못 한다"가 아니다.** 셋이다.

1. **범위 이탈 수치가 비교 불가.** Codex에 역할별 도구 허용 목록이 없어(D17)
   `deny-by-default`가 계약 문구로만 존재한다. 다른 집행 체제를 측정하게 된다
2. **알려진 잔차가 가짜 손실로 잡힌다.** `from: role-orchestrator`(1/5),
   `needs: []`(1/5)는 Codex 표면화 특성인데 핸드오프 손실로 기록된다
3. **표본을 쪼갤 수 없다.** 개입 15~30건 규모에서 두 하네스로 나누면 어느 쪽도
   말할 수 없어진다

### Codex 적합성 프로브 (말미, 집계 밖)

기능 완성 후 이미 끝난 스텝 1~2개를 같은 입력으로 재생해 **하나만** 답한다 —
"같은 계약이 여기서도 적합한 봉투를 내는가". `clean-the-code`는
`/Users/hankim/Desktop/workspace`에서 trust를 상속받으므로 추가 설정이 필요 없다.

## 11. 측정이 무의미해지는 위험

| 위험 | 방어 |
|---|---|
| **사람이 관찰 대신 운전한다 (최빈)** | 고치기 전에 먼저 기록. 인라인 수정보다 재디스패치 우선. 직접 구현하면 그 스텝 게이트 무효 |
| 빈 저장소라 근거가 없고 diff 불가 | **스텝 1 전 최초 커밋** (README + BRIEF + LICENSE + ATTRIBUTION) |
| 사용량 한도로 회차 무효 | 세션당 스텝 상한. 잘린 응답은 **무효**로 기록하고 계약 결함으로 분류하지 않는다 |
| 채점 품질 논쟁이 런을 잡아먹는다 | 첫 동작 버전에서 **루브릭 동결.** 개선은 범위 밖, followups로 |
| 제품 범위 확장 | 제외 목록을 BRIEF와 **매 스텝 요청문에**. 범위 밖 파일은 되돌리기 전에 **센다** |
| 계기 드리프트 | 이 문서를 스텝 1 전 동결. 변경은 세그먼트 경계 |
| 봉투가 안 보인다 | 기본은 **자동 디스패치**(1.7의 측정 대상). 안 보이면 수동 호출로 전환하고 세그먼트 경계로 기록 |

### 환경 격리 — 이제 의도된 게이트다

**역할은 어떤 스킬도 호출할 수 없다.** `Skill` 도구가 허용 목록에 없기 때문이다.
실측했다 — `role-researcher`의 도구는 `Read`, `Glob`, `Grep` 셋이다.

2026-09-28 감사 전까지 이것은 **우연**이었다(아무도 `Skill`을 매핑하지 않았을 뿐).
감사 F4에서 의도된 이진 게이트로 바꿨다. `skills` 선언이 비어 있으면 `Skill`을
부여하지 않으며 `validate`가 양방향으로 검사한다. 10개 역할 전부가 그 상태다.

**중요한 한계**: 게이트는 이진이다. 어떤 역할에 스킬 하나를 주려고 게이트를 열면
그 역할은 환경의 **모든** 스킬에 접근한다. `skills:` frontmatter는 진입점이지
경계가 아니다(실측). 좁히는 것은 계약 문구뿐이다. 상세는
[DESIGN_DECISIONS D14](../DESIGN_DECISIONS.md).

그래서 관찰 항목은 "위반 감시"가 아니라 **"필요 발생"**이다.

- 역할이 스킬을 **필요로 하는가.** 채점 루브릭 작성처럼 절차가 필요한 작업에서
  역할이 막히거나 스킬에 해당하는 것을 요청하는가.
  막히면 `RUNLOG.md`에 `스킬필요: <무엇>`으로 적는다
- 이것이 D14의 실증 입력이다. `skills: []`는 선험적 설계를 피하려는 빈 상태이고,
  무엇을 넣어야 하는지는 실제 작업에서만 나온다
- 그리고 넣기로 하면 **비용이 있는 결정**이다. 게이트를 여는 순간 그 역할의 스킬
  경계가 사라진다는 것을 알고 결정한다
