# Phase 1 감사

**2026-09-28. 감사 완료 — 조치 미착수.**

## 왜 이 문서가 있는가

Phase 1은 완료로 기록됐다. 그런데 Phase 2 착수 준비 중에 결함이 계속 나왔다.
문제는 결함의 개수가 아니라 **발견 방식**이다.

| 발견 | 어떻게 발견했나 |
|---|---|
| 고정 체인 3곳 | 계획 검토 중 우연히 |
| 고정 체인 2곳 더 | 배포물을 렌더해 보다가 |
| `install` 경로 오보 | 대상 저장소에 설치하다가 |
| `doctor`가 역할 디렉터리 미검사 | 위 결함을 고치다가 |
| 스킬 허용 목록 부재 | 사용자가 지적 |

**전부 사고다.** 내가 우연히 부딪친 것만 나왔고, 부딪치지 않은 것은 아직 모른다.
이 방식으로는 "이제 다 고쳤다"를 말할 수 없다. 그래서 완료 주장을 하나씩 짚는
감사로 바꾼다.

**이 감사가 끝나기 전까지 Phase 2를 실행하지 않는다.**

## 감사 방법

Phase 1의 완료 기준 43개(1.0~1.9)에 대해 셋을 묻는다.

1. **주장이 무엇인가** — 무엇이 참이라고 말했는가
2. **근거가 무엇인가** — 실측 / 기계 검사 / 주장만
3. **근거의 범위가 주장의 범위와 같은가** — D12 원칙 4

3번이 이 감사의 핵심이다. 1.7이 뚫린 방식이 정확히 그것이었고, 나는 그 원칙을
D12에 적은 직후에 같은 실수를 반복했다.

추가로 넷째 질문을 둔다. 1회 실측은 그 시점의 사실이지만 회귀를 막지 못한다.

4. **회귀 보호가 있는가** — 지금 깨지면 무엇이 알려주는가

### 하네스 통과율의 실제 의미

이것이 F1~F3의 합산 결과이며 따로 적을 값이 있다.

케이스 7개는 라우팅 4개(R1·R2·R3·R5)와 역할 3개(R4·R6·R7)로 갈린다.
라우팅 케이스만 `judgeRun`을 돌리고, 거기서 검사 6개가 나온다. 그중 **3개가 공허하다.**

```
라우팅 케이스 4개 × 공허 검사 3개 = 12
```

| 기록 | 보고된 값 | 공허 | 실제 판정력 |
|---|---|---|---|
| `2026-09-24T02-13-53` (1.8 완료 근거) | 51/51 | 12 | 39 |
| `2026-09-28T05-24-06` (1.7 후속) | 56/58 | 12 | 44/46 |

**"51/51 통과"는 검사 51개가 판정했다는 뜻이 아니다.** 12개는 입력이 하드코딩된
빈 배열이어서 어떤 실행에서도 실패할 수 없다. 로드맵과 DEVLOG에 이 숫자를
회귀 없음의 근거로 여러 번 썼으므로, 그 근거의 강도를 정정해야 한다.

## F1. `tools.declared_only`가 공허하다

**주장** (1.5 완료 기준): `- [ ] 선언되지 않은 도구를 역할이 사용하면 탐지된다 — 1.6 하네스에서 구현`

체크박스는 **미완료로 옳게 남아 있다.** 문제는 다른 데 있다.

**실제 상태**: 판정기에 검사가 있고(`judge.js:330`), 단위 테스트가 합성값으로
돌리고(`judge.test.js:137`), 결과 출력에 `tools.declared_only`가 통과로 찍힌다.
그런데 실행기가 입력을 채우지 않는다.

```js
// tests/eval/run.js — 두 경로 모두
undeclaredTools: [],   // 하드코딩
```

`observe()`는 `toolsUsed`를 실제로 수집한다. 선언과 대조하는 코드가 없을 뿐이다.

**왜 이렇게 됐는가**: 코드의 주석이 이유를 적어 뒀다.

> 부모 스트림에는 서브에이전트 내부 도구가 나타나지 않으므로 여기서 관찰되는
> 도구는 메인 세션의 것이며 역할 계약의 대상이 아니다.

**이 이유는 사실이다.** 부모 스트림에 서브에이전트 내부 도구 호출은 없다.
그러니 "관찰할 수 없어서 판정하지 않는다"는 정직한 선택이었다.

**그럼 무엇이 결함인가**: 판정하지 않기로 했는데 **통과로 보고한다.** Codex의
라우팅은 같은 상황에서 `routing.not_observable`이라는 별도 검사로 "신호가 없어
판정하지 않는다"를 명시한다. 도구에는 그 처리가 없다. 관찰 불가와 위반 없음이
같은 `[ok]`로 찍히고 통과 수에 들어간다.

**조치**: `tools.not_observable` 유형을 만들어 통과 수에서 분리한다. Codex 라우팅의
선례가 이미 있으므로 새 설계가 아니다. 실제 판정이 가능한지는 별건이다 —
서브에이전트 도구를 관찰할 경로가 있는지 조사해야 하며, 없으면 없다고 기록한다.

## F2. `scope.out_of_scope_respected`가 공허하다

**주장** (D6): `out_of_scope` 위반은 감지 시 즉시 중단한다.

**실제 상태**: F1과 같은 모양이다. `outOfScopeViolations: []`가 두 경로에 하드코딩됐다.

**F1보다 나쁜 점**: 데이터가 이미 있다. `observe()`가 `git status`로
`changedFiles`를 계산한다(`run.js:244`, `run.js:339`). 그런데 **어디에서도 소비되지
않는다.** 봉투의 `out_of_scope`도 파싱되어 있다. 교집합을 구하는 코드만 없다.

F1은 관찰이 불가능해서 못 했고, F2는 **관찰해 놓고 연결하지 않았다.**

이것은 Phase 2의 핵심 지표이기도 하다. 계기 문서는 범위 이탈을
`git diff --name-only ∩ out_of_scope`로 센다고 적었다. 같은 계산을 하네스가 할 수 있다.

**조치**: `changedFiles`와 봉투 `out_of_scope`를 대조해 `outOfScopeViolations`를 채운다.
주의: 역할 모드에서만 봉투가 있으므로 라우팅 모드에서는 여전히 판정 대상이 아니다.
그 경우도 통과가 아니라 미판정으로 분리한다.

## F3. `setup.roles_loaded`가 Claude에서 공허하다

**주장** (1.2 완료 기준): `- [x] Claude 실제 로드 검증 통과. 서브에이전트 6개 + 오케스트레이터 스킬 전부 노출`

**이 주장 자체는 참이다.** 1.2에서 수동으로 확인했고, 나는 2026-09-28에
`clean-the-code`에서 다시 확인했다 — `init` 이벤트에 역할 에이전트 9개와
`role-orchestrator` 스킬이 모두 있다.

**결함은 회귀 보호다.** `observe()`의 반환값에 `setupErrors`가 없다.

```js
return { rolesSelected, toolsUsed, steps, toolCalls, finalText,
         transcript, runError, sawResult, changedFiles };
// setupErrors 없음
```

`judgeRun`은 `observed.setupErrors || []`를 읽으므로 Claude에서는 항상 빈 배열이다.
게다가 `observe()`는 `event.type === "system"`을 전부 건너뛴다 — 로드 오류가 나타날
자리가 바로 거기다.

**왜 중요한가**: 1.2와 1.5에서 정확히 이 유형의 결함을 두 번 겪었다.
Claude 타깃이 로드되지 않는 파일을 만들었고, Codex 역할 TOML 9개가 `web_search`
boolean으로 전부 무효였다. 둘 다 **설치는 성공했고 `doctor`는 통과했다.**
그 유형을 잡을 자동 검사가 지금도 Claude에는 없다.

**조치**: `observe()`가 `system` 이벤트에서 역할 로드 실패 신호를 수집해 반환한다.
`init` 이벤트의 에이전트·스킬 목록을 manifest와 대조하는 것이 더 직접적이다 —
그 목록은 실제로 있고 내가 방금 읽었다.

## F4. D14 스킬 바인딩이 전면 미구현이다

사용자가 지적한 항목이며, 감사에서 가장 범위가 넓다.

**주장** (1.5): `- [x] manifest 역할에 skills 키를 추가한다 (역할이 호출 가능한 절차의 허용 목록). 초기값은 빈 배열.`

**실제 상태**: 선언은 있고 아무 일도 하지 않는다.

| 층 | 상태 |
|---|---|
| manifest `skills` | 10개 역할 전부 `[]` |
| 어댑터 `skills` 매핑 | **없음** (`skillsDir` 경로 키뿐, 무관) |
| `cli.js` 렌더 | **없음.** `Array.isArray(role.skills)` 검사만 |
| `Skill` 도구 매핑 | **없음** |

1.5는 연기 이유를 기록해 뒀다.

> `skills` 매핑은 모든 역할의 `skills`가 빈 배열이라 아직 필요 없다
> (D14: 선험적 설계 금지). 역할이 실제로 스킬을 선언할 때 추가한다.

**그 연기가 놓친 것**: 1.1의 조사는 이미 `skills:` frontmatter가 **네이티브**라고
판정했고 렌더링하겠다고 적었다(`HARNESS_CAPABILITIES.md:75`). 그런데 렌더가 없으면
빈 배열의 의미가 뒤집힌다. 허용 목록이 비었으면 "아무것도 허용 안 함"인데,
렌더되지 않으면 "제한 없음"이 된다. **선언이 말하는 것과 배포물이 하는 것이 반대다.**

도구는 이 문제가 없다. `toolPolicy: deny-by-default`가 `tools:` frontmatter로
실제 렌더된다. 스킬만 정책이 없다.

### 실측: 지금 역할은 스킬을 호출할 수 없다

`Skill` 도구 매핑이 없으므로 어떤 역할의 `tools:`에도 `Skill`이 없다.

```
role-analyst      tools: Read, WebSearch, WebFetch, Glob, Grep
role-researcher   tools: Read, Glob, Grep
role-developer    tools: Read, Write, Edit, Grep, Bash, Agent
...
```

격리된 프로젝트에서 `role-researcher`에게 스킬 호출을 지시해 확인했다.
역할의 답: 도구는 정확히 `Read`, `Glob`, `Grep` 셋이고 `Skill`은 목록에 없다.
호출을 발행하지 못했으므로 오류 문자열도 없다.

그 역할이 스스로 덧붙인 구분이 정확하다. **"실패가 아니라 호출 자체의 부재이며,
둘은 다른 상태다."**

### 따라서 격리는 우연히 성립하고 있다

외부 플러그인 스킬을 역할이 쓸 수 없는 것은 허용 목록이 막아서가 아니라,
`Skill` 도구를 아무도 매핑하지 않았기 때문이다. 누가 패키지 스킬 하나를 주려고
`Skill` 매핑을 추가하는 순간, 그 역할은 **환경의 모든 스킬**에 접근한다.
범위를 좁힐 수단이 없다.

사용자의 지적이 정확히 이 지점이다. 특정 스킬 이름을 금지하는 방식은
그 이름을 쓰지 않는 경우를 못 막는다. 필요한 것은 허용 목록이다.

### 조치 (설계 필요, 이 감사에서 결정만)

1. `Skill` 도구 매핑을 추가하되 **`skills` 선언이 비어 있으면 부여하지 않는다**
2. `skills`가 비어 있지 않으면 타깃 네이티브 구문으로 렌더한다
   (Claude `skills:` frontmatter, Codex `[[skills.config]]` — 1.1이 조사한 그대로)
3. **스킬을 추가하는 절차를 문서화한다.** 지금은 절차가 없어서 필요해지면
   임기응변이 된다. 선언 → 매핑 → 렌더 → 검사의 네 층을 모두 지나야 한다
4. `validate`가 이 불변식을 검사한다 — `skills`가 비었으면 렌더에 `Skill`이 없고,
   비어 있지 않으면 선언된 것만 있다

이것은 D14의 구현이며 결정 변경이 아니다. 다만 "빈 배열의 의미"를 D14에 명시해야
한다 — 비었다는 것은 유보가 아니라 금지다.

## F5. 내용 불변식을 소스에서만 검사한다

이것이 1.7이 뚫린 구조적 원인이고, 개별 패치로 닫히지 않는다.

**현재 구조**:

| 검사 | 대상 |
|---|---|
| `validateSkill` | `skills/<role>/SKILL.md` — **소스** |
| `validateAdapter` | 렌더 결과 — **배포물** |

`validateAdapter`는 배포물을 제대로 본다. 출력 키, frontmatter 형태, TOML 유효성,
`web_search` 열거값, 권한 키, 도구 가용성 조건문까지 렌더에 대고 검사한다.

**그런데 내용 불변식은 전부 `validateSkill`에 있다** — 즉 소스만 본다.

- `## Activation` / `## Done Criteria` / `## Stop Conditions` 존재
- 봉투 필드와 `from:` 일치
- Stop Conditions의 타역할 지명 금지 (D16)
- 고정 체인 부재 (내가 2026-09-28에 추가한 5종 포함)

대부분의 타깃에서 렌더는 소스 + 헤더이므로 보통은 일치한다. **보통은.**
1.7의 완료 기준은 "저장소와 **전 타깃 배포물** 어디에도"였고, 근거는 소스 검사
통과였다. 그래서 체인 2곳이 배포물에 남았고, 내가 손으로 렌더해 grep해서야 나왔다.

**조치**: 내용 불변식을 `validateAdapter` 쪽으로 옮기거나, 렌더 결과에도 같은 검사를
적용한다. 그러면 "배포물에 없다"를 주장할 때 배포물을 근거로 쓸 수 있다.

일반 규칙으로 승격할 값이 있다. **주장의 대상이 배포물이면 검사의 대상도 배포물이다.**

## F7. 내가 메인 세션 관측으로 서브에이전트 능력을 단정했다

감사 중에 내 오류를 찾았으므로 같은 기준으로 적는다.

`clean-the-code`에서 `init` 이벤트를 읽고 `ff-review:*` 스킬 목록을 봤다.
거기서 **역할이 그 스킬을 볼 수 있다**고 결론내고 두 곳에 사실로 적었다.

- `clean-the-code/BRIEF.md` 제약 3번: "이 환경에는 `ff-review:*` 스킬이 실제로
  로드돼 있다... 보인다고 쓸 수 있는 것이 아니다"
- `phase2/README.md` §11: "역할이 `ff-review:*` 스킬을 호출하면..."

**틀렸다.** `init` 이벤트는 메인 세션의 도구·스킬 표면이다. 서브에이전트의 표면은
자기 `tools:` frontmatter가 정하고, 거기에 `Skill`이 없다(F4 실측).

1.2b에서 겪은 것과 같은 유형의 오류다. 그때는 모델에게 에이전트 목록을 물었는데
모델이 내 `AGENTS.md`를 읽어서 답했고, 나는 그것을 로드 증거로 읽었다.
**관측 지점이 주장 대상과 다른 층일 때 생긴다.**

**조치**: 두 문서를 정정한다. BRIEF의 규칙 자체(위임 금지)는 유지할 값이 있으나
근거 문장이 틀렸고, 계기 문서의 관찰 항목은 전제가 무너졌으므로 다시 쓴다.

## F8. TOML 유효성을 실제 파서로 검사하지 않는다

**주장** (1.2 완료 기준): `- [x] 생성된 TOML 6개 tomllib 파싱 및 sandbox_mode 일치 확인`

**주장은 당시 참이었다.** 수동으로 `tomllib`에 넣어 봤다.

**결함 둘**:

1. **회귀 보호가 없다.** 저장소 어디에도 실제 TOML 파서를 쓰는 검사가 없다
   (`tomllib` / `toml.load` / `parseToml` 전부 0건). `validate`가 보는 것은
   문자열이다 — 필수 키 존재, `"""` 개수 짝, `web_search` 열거값.
2. **수치가 낡았다.** 6개가 아니라 9개다.

**왜 중요한가**: 1.5의 Codex 결함이 정확히 이 틈으로 들어왔다. `web_search = true`가
열거값이 아니어서 역할 TOML 9개가 전부 무효였고, **설치는 성공했고 `doctor`는
통과했다.** 그때 추가한 것은 `web_search` 값 하나를 보는 검사다. 같은 유형의
다른 TOML 오류는 지금도 지나간다 — 이스케이프되지 않은 따옴표, 잘못된 배열 구문,
중복 키.

문자열 검사로 TOML 유효성을 주장하는 것은 **정규식으로 파싱을 대신하는 것**이다.
`"""` 개수를 세는 검사가 이미 그 냄새를 낸다.

**조치**: 렌더 결과를 실제 TOML 파서에 넣는다. Node에 내장 파서가 없으므로
`python3 -c "import tomllib; tomllib.loads(...)"`를 쓰거나 최소 파서를 넣는다.
smoke가 이미 `python3`를 쓸 수 있는 환경을 가정하는지 확인하고 결정한다.

## F9. `doctor`는 파일 존재만 검사한다

**주장**: 명시된 완료 기준은 아니다. `doctor`는 소비자가 설치 상태를 진단하는 도구다.

**실제 상태**: 통과 조건 14개가 거의 전부 `fs.existsSync`다.

| 검사 | 통과 조건 |
|---|---|
| 스킬 파일 | `every(existsSync)` |
| 에이전트 파일 | `every(existsSync)` |
| specs / workflow | `existsSync` |
| 레거시 디렉터리 | 개수 0 |
| guidance 블록 | 마커 문자열 포함 |
| lint / test / typecheck | 스크립트 키 존재 |

**내용을 검사하는 것이 하나도 없다.** 역할 파일 9개가 전부 무효여도, 파일이 그 자리에
있으면 전부 `[ok]`다.

**이것이 1.5에서 실제로 일어났다.** DEVLOG에 그 문장이 그대로 있다 —
"설치가 성공하고 `doctor`가 통과했다(파일 존재만 검사)". 교훈을 기록했지만
`doctor`는 고치지 않았고, 대신 `validate`에 값 하나를 보는 검사를 넣었다.

**중요한 비대칭**: `validate`는 **개발자가** 저장소에서 돌리는 검사이고,
`doctor`는 **소비자가** 자기 프로젝트에서 돌리는 검사다. 소비자는 `validate`를
돌릴 수 없다. 그래서 무효한 설치를 가진 소비자에게는 진단 수단이 없다.

**조치**: `doctor`가 설치된 역할 파일을 최소한 파싱한다. Claude은 frontmatter에
`name`이 있고 역할 이름과 일치하는지, Codex는 TOML로 파싱되는지. 렌더러가 이미
같은 검사를 `validate`에서 하므로 공유할 수 있다.

## 일반화 — 왜 같은 유형이 반복됐나

개별 발견보다 이 셋이 중요하다. 아홉 건이 전부 여기서 나왔다.

1. **근거의 층이 주장의 층과 다르다.**
   소스 검사로 배포물을 주장했다(F5). 메인 세션 관측으로 서브에이전트를 주장했다(F7).
   문자열 검사로 TOML 유효성을 주장했다(F8). 파일 존재로 설치 정상을 주장했다(F9).
   → **규칙: 주장의 대상이 X면 검사의 대상도 X다.**

2. **관찰 불가와 위반 없음이 같은 통과로 보고된다.**
   F1·F2·F3이 모두 이것이다. Codex 라우팅만 `not_observable`로 분리했고 나머지는 안 했다.
   → **규칙: 판정하지 않은 것은 통과가 아니다. 통과 수에서 분리한다.**

3. **연기한 항목을 아무도 다시 보지 않는다.**
   "1.6에서 구현", "1.8 이후 검증", "역할이 실제로 스킬을 선언할 때 추가"가 모두
   그 단계가 지나고도 열려 있거나 상태가 낡았다(F4·F6).
   → **규칙: 연기는 대상 단계의 완료 기준에 항목으로 들어가야 한다.**

세 규칙은 D12에 원칙으로 올릴 값이 있다. 원칙 4(검사의 범위)는 1번의 특수한 경우다.
