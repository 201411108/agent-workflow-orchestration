# Feature Orchestrator

사용자 요청을 가장 작은 유효 역할 체인으로 분류하고, 선택한 프로젝트
custom agent에 순서대로 위임한다. 단순 질의, 파일 읽기, 사소한 단일 수정은
이 스킬과 역할 체인을 생략할 수 있다.

## 라우팅

| 요청 분류 | 활성 역할 |
|---|---|
| UI가 포함된 신규 기능 | `planner → designer → developer` |
| UI가 없는 신규 기능 | `planner → developer` |
| UI/UX 개선 | `designer → developer` |
| 버그 수정·리팩터링 | `developer` |
| 기획 검토 | `planner` |
| 디자인 리뷰 | `designer` |
| 복합 요청 | 요청에 필요한 역할 조합 |
| 단순 질의·파일 읽기·사소한 수정 | 오케스트레이터 생략 가능 |

복합 요청은 요청 전체를 기계적으로 세 역할에 보내지 않는다. 제품 범위 결정은
`planner`, 화면·상호작용 결정은 `designer`, 코드·테스트 변경은 `developer`가
필요한 경우에만 활성화한다.

## 실행 절차

1. 적용되는 `AGENTS.md`, 기존 SSoT 문서, 관련 코드와 테스트를 먼저 확인한다.
2. 실행 전에 사용자에게 `작업 분류: <분류> | 활성 역할: <순서 또는 없음>` 형식으로
   한 줄 안내한다.
3. 활성 역할을 동일한 이름의 프로젝트 custom agent에 위임한다. 앞 역할의 결정이
   필요한 역할은 앞 역할 완료 후 시작한다.
4. 전체 대화나 원시 로그를 넘기지 말고 아래 인계 패킷만 다음 역할에 전달한다.
5. 모든 활성 역할이 끝나면 메인 에이전트가 결과를 검토·통합하고, 변경과 검증을
   직접 확인한 뒤 최종 결과를 작성한다.

## 역할 인계 패킷

```markdown
### 역할 인계
- 목표:
- 확인된 사실:
- 결정 사항:
- 가정:
- 리스크:
- 미결정 사항:
- 미검증 항목:
- 다음 역할 입력:
```

- `확인된 사실`에는 파일, 명령 결과, 사용자 제공 정보처럼 근거가 있는 내용만 쓴다.
- `가정`은 사실처럼 표현하지 않고 채택 이유와 영향 범위를 함께 쓴다.
- 실행하지 않은 검사나 확인하지 않은 동작은 `미검증 항목`에 남긴다.
- 다음 역할이 다시 전체 탐색을 하지 않도록 결정과 리스크를 압축하되, 근거 경로는
  보존한다.

## 위임 실패

서브에이전트 도구가 없거나 선택한 custom agent를 시작할 수 없으면 일반 추론으로
역할 실행을 가장하지 않는다. 사용자에게 `상태: degraded`와 함께 사용할 수 없는
역할, 누락되는 검토, 결과의 제한을 알린다. 안전하게 수행 가능한 메인 에이전트
작업은 계속할 수 있지만, 위임이 성공한 것으로 보고하지 않는다.
